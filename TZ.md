# TZ — Техническое задание по расширению поддержки игровых движков

> Версия: 0.3.4 · Дата: 2026-08-03 · Автор: новый Python-разработчик отдела
> Статус: **на рассмотрении** — читайте финальный раздел «Рекомендации и приоритеты».

---

## 1. Контекст и цель

OctopusBridge сегодня переводит и модифицирует игры трёх движков:

| Движок | Язык сценариев | Транспорт живого перевода |
|---|---|---|
| RPG Maker MV/MZ | JavaScript (JSON-данные) | CDP (Chromium/NW.js) |
| Ren'Py | Python (`.rpy` → bytecode) | Frida-инъекция Python-агента |
| Twine/SugarCube | HTML+JS (`<tw-storydata`) | HTTP+WS мост (любой браузер) |

Задача: **исследовать, для каких ещё игровых движков мы можем добавить поддержку**, и
определить приоритеты так, чтобы усилия давали максимум пользы для пользователей.

Ключевой момент: движков «на Питоне» (как Ren'Py) почти нет — Python почти не
используется конечными играми. Но наш инструмент **сам написан на Python**, поэтому
ему по силам любые движки, где тексты лежат в *разбираемых текстовых форматах* либо
имеют *существующие Python-решения для распаковки*. Именно с этой точки зрения и
отобраны кандидаты.

---

## 2. Как устроен движковый модуль (контракт)

Чтобы новый движок попал в приложение, достаточно:

1. Класс-наследник `EngineModule` (`app/engines/base.py`):
   - `key`, `title`, `features` (`files`/`live`/`cheats`/`resources`/`font`/`maps`);
   - `detect(game_dir) -> int` — вес уверенности (0 = не наш движок);
   - `extract(game_dir) -> list[TranslationEntry]`;
   - `apply(game_dir, entries, target_lang) -> stats`;
   - `ui_tabs(main_window)` — движковые вкладки GUI.
2. Регистрация в `app/engines/registry.py`.
3. Парсер данных в `app/core/<engine>/parser.py`.
4. Опционально — «щупальце» (tentacle) в `app/core/tentacles/` и/или транспорт в
   `app/transport/` для живого перевода.

То есть для каждого кандидата главный вопрос — **насколько просто написать
extract/apply**, а живой перевод — бонус, который не блокирует релиз.

## 3. Каталог кандидатов

### 3.1 Прямые родственники Python (низкий приоритет)

Python-движки в массовом дистрибуции не существуют: игрок приходит в `.exe`
(иногда через PyInstaller/Nuitka), а исходник зачастую отсутствует. Это делает
`extract/apply` ненадёжными и хрупкими. Особенности:

- **Pygame / Pygame-ce / Pygame Zero** — самая массовая ниша: демки, game jam,
  учебные игры. Тексты обычно в `.py`-исходниках или `.json`-ресурсах.
  → *Можно поддержать только файловую выгрузку строк из `.py`/`.json`*, но без
  гарантии качества (много ложных срабатываний на код). Низкий приоритет.
- **Panda3D / Ursina / Arcade / Kivy** — нишевые, компилируются в exe.
  → *та же история: низкий приоритет*.
- **Ren'Py** — уже поддерживаем стабильно, включая live-перевод и читы. Точка.

**Вывод:** «Python-движки» сами по себе не приносят массовых игр. Имеет смысл
дополнительно развивать **Ren'Py** (уже есть) и не распылять силы на остальные.

---

### 3.2 RPG-серия (не-Python, но тексты читаемы) — высокая ценность

**Вывод по этой группе:** серия **RPG Maker XP/VX/Ace** — это огромный пул
японских RPG-новелл, который сегодня мы не открываем вовсе. Форматы: Ruby Marshal
(`.rxdata`/`.rvdata`/`.rvdata2`) и архивы `.rgssad`/`.rgss2a`/`.rgss3a`.

Сложность: средняя. Существующие решения:
- `RPG-Maker-Translator` (Ruby) — выгружает JSON, патчит.
- `rvpacker` / `rvpacker-txt` — парсит тексты в `.txt` и обратно.
- `RPGMTL` (Python!) — уже умеет Ruby Marshal и RGSSAD — можно подсмотреть подход.

**Что делать:**
1. Реализовать распаковщик `.rgssad` (легко, XOR+Zlib) и читатель Marshal
   (в Python есть образцы: `rubymarshal`, `rpgmaker-mv-decrypter`-подобные
   проекты; парсинг Marshal для этих форматов реализован в ряде open-source
   инструментов).
2. Явный формат выгрузки: JSON (как в RPG-Maker-Translator) — уже знакомый нам
   формат из RPG Maker MV/MZ.
3. Live-перевод: Frida для RGSS-процесса потенциально, но **не обязательно** для
   первой версии — файловый режим приносит 90% ценности.

**Приоритет: высокий.** Конкурирует с Kirikiri за первое место в очереди.

---

### 3.3 KiriKiri / KAG (японские визуальные новеллы) — высокая ценность

Не Python, но наследующий многие игры японских визуальных новелл.

- Форматы: архивы `.xp3`, сценарии `.ks` (текст с тегами `[name]`, `[ruby]`,
  `[ch]`, `[button]`, `[jump]` и т.п.), частично бинарный PSB-датабаз сценария.
- Известные помощники (в том числе на Python):
  - `RPGMTL` (Python) умеет KAG `.ks` и `.tjs`.
  - `toto` (Python) — extract/insert для `.ks`/`.soc`.
  - есть открытые Python-реализации чтения/записи `.xp3`.
- Сложность: средняя (основная сложность — кодировки Shift-JIS → UTF-8),
  маскирование тегов — у нас такая механика уже есть (`\C[8]`, `<center>`).
- Live-перевод: возможно через AfterInit2.tjs-хук / patch.xp3 (загружается
  поверх) — это ближе к «файловому» патчу, чем к инъекции.

**Приоритет: высокий** (v0.4, после RPG Maker-классики или параллельно).

---

### 3.4 TyranoBuilder / TyranoScript — средняя ценность

- Движок визуальных новелл, формат — KAG-подобный `ks`/`tjs`, распространяется
  чаще с открытыми файлами.
- Простота: высокая, если файлы не упакованы; но такой же тагомат, как KiriKiri.
- Уникальных сложностей нет. **Приоритет: средний.**

### 3.5 Второстепенный класс (средняя ценность; делать только по заказу/образцу)

| Движок | Формат | Сложность | Комментарий |
|---|---|---|---|
| **NScripter / ONScripter** | `.txt`-скрипт (NJS), `nscript.dat` | низкая | наследие фан-переводов и старого онс-сообщества |
| **Wolf RPG Editor** | `.arc` (бинар) | высокая–средняя | есть Python-распаковщик `WolfDec`; форматы для текста знать надо — много ручной работы |
| **YU-RIS (AliceSoft)** | `.ybn` / `.ypf` | средняя | RPGMTL умеет из коробки — можно наследовать логику |
| **LiveMaker / VN Maker** | `.vproj` + ресурсы | высокая | нет готового Python-ридера |
| **LÖVE (Love2D)** — Lua | `.zip`-игры с `.lua` | средняя | тексты в Lua читаются, но патчинг кода рискован |
| **GameMaker (GMS)** | `.yy` JSON + ресурсы | средняя | зависит от версии компилятора |
| **Godot** | `.tscn`/`.tres`/GDScript | средняя | есть официальная локализация (`.po`/`.csv`) — можно выгружать строки в её формат; не инжектировать |
| **Unity** | `.assets` | сверхвысокая | IL2CPP/Mono obfuscation; не берём на этот этап |
| **Unreal** | байты мультиформат | сверхвысокая | не берём на этот этап |

## 5. Рекомендуемый план работ (что делать первым)

> Исполнитель один (я), поэтому порядок важен. Цель — первый новый движок в
> релизе **0.4, не распыляясь на 10 сразу**.

1. **MVP: RPG Maker XP/VX/Ace (файловый режим).**
   - [ ] Реестр: добавить `RpgMakerClassicModule` (`detect` по `Game.exe` +
       перечислению `Data/*.rvdata2|rxdata|rvdata` и/или наличие `Game.rgss3a`).
   - [ ] Распаковщик `.rgssad`/`.rgss2a`/`.rgss3a` (XOR-ключи известны, Zlib).
   - [ ] Читатель–запись Ruby Marshal для `RPG::*` (переиспользовать JSON-модель
       как у MV/MZ, но через послойную нормализацию).
   - [ ] `extract/apply` + маскирование кодов (в RPG Maker классика — те же
       `\V[n]`/`\N[n]`/`\C[n]`, поддержка уже есть в MV/MZ).
   - [ ] Классы для GUI: свои вкладки с ресурсами именами героев.
   - [ ] Сохранение переводов в общую память (SQLite) — как у MV/MZ.
   - [ ] Регресс-тесты на образце игры XP/VX/Ace.
   - [ ] Итог: 0.4 поддерживает **5 типов игры** (MV/MZ + классика + Ren'Py + Twine).

2. **Второй: KiriKiri/KAG (файловый режим).**
   - [ ] XP3-unpack + чтение `.ks` (кодировки Shift-JIS/UTF-8), маскирование
       KAG-тегов.
   - [ ] Экспорт в наш формат записей, патч обратно (patch.xp3 / loose-файлы).
   - [ ] Маскирующий механизм и модель записей переиспользуется с высокой долей
       вероятности.

3. **По остатку времени: NScripter/ONScripter и Tyrano (низкая сложность).**

4. **НЕ в этом цикле:** Wolf, Unity, Unreal, Pygame-детекты и Godot — оставляем в
   бэкелог.

## 6. Риски и ограничения

- **Маршал-файлы менялись между XP/VX/Ace**: структуры `RPG::*` и правила
  сериализации различаются между версиями — нужен адаптер под каждый вариант.
- **KiriKiri**: кодировки + большое количество индивидуальных шифров на `.xp3`
  у коммерческих игр. В MVP ограничиваемся незашифрованными/разбираемыми
  архивами и документируем ограничения.
- **Live-режим** дорог для любого не-Python движка: файловый (патчевой) режим
  дешевле. Делаем его второй очередью, не блокируя релиз.
- Юридический аспект: инструмент модифицирует игры; инъекции в память всё ещё
  экспериментальны для классических RPG-процессов — поддерживаем политику
  «только для своих игр / с разрешения».
- Архитектурный риск: файловые форматы эволюционировали со временем — нужны
  референтные «игры-образцы» для тестов.
